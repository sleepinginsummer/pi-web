# Models and provider auth

## Model defaults for new sessions
`GET /api/models` returns `defaultModel` from `~/.pi/agent/settings.json`; `ChatWindow` pre-selects it for new sessions. Browser model/thinking picks are applied atomically while the AgentSession is built and are **session-scoped**: neither startup nor a mid-session `set_model` / `set_thinking_level` writes `settings.json`, as pi's `/model` and `/thinking` persist only on Ctrl+S (otherwise a one-off pick becomes the TUI's default too).

草稿创建时，工具配置在输入框初始化或 cwd/worktree 切换的那一刻写入 `SET_TOOLS`，以后创建只读取该 cwd 的草稿记录；浏览器偏好不能改变已经展示过的名单。worktree 改变时 `updateDraftCwd()` 推进 `sessionKey`，按导航代次重建 ChatWindow，旧 runtime ID、本地切模引用和异步回调留在原实例；目标草稿从自己的共享状态恢复，正文与附件继续由按 cwd 保存的 draft-store 恢复。创建等待只按目标 cwd 读取共享任务，不能用另一 cwd 的本地任务与同号版本比较。直接打开 `?cwd=` 尚无镜像时，读取回退到当前控制状态，再通过同一事件入口补齐镜像。

自动推荐保存 `recommendationModel`（provider + modelId），随默认模型目录刷新重新计算；新模型没有推荐时清除旧值并恢复 `auto`。创建请求同时传 `thinkingLevelModel`（provider/modelId）；普通启动已知 `startupModel` 时，创建前校验推荐并通过 SDK 的 `thinkingLevel` 构造参数初始化，避免在 `session_start` 和 UI 绑定前额外触发 `thinking_level_select`；只有 SDK 自行选模（`startupModel` 为空）时才在 `createAgentSessionFromServices()` 返回后按 `inner.model` 校验并应用。Fast 开关、扩展绑定及 reload 后的恢复都进入与手动改档、切模共用的 `enqueueModelPreference` 队列。同身份副本通过 host.prepareSameModel 等待 runtime.checkAuth 并返回 validate/commit；reconcile 从 await 恢复后、任何状态写入之前同步调用 validate，再核对模型引用和磁盘新鲜度；需要保存的 Fast 状态成功落盘后，才同步替换 Agent state.model 的私有副本并更新 applied，中间不再 await。不调用 SDK setModel，也不改思考档位，避免失败前已经写入默认 thinking_level_change、仅恢复内存后重开仍读到错误档位。同模型副本的鉴权未结束时，后到的改档仍须排队，不能提前确认。真正切换模型身份时仍用 SDK setModel 与原生定档规则，withModelAuthWriteGuard 的每次成功鉴权（含扩展并发调用）都先做公共可写性检查；另将 host.setModel 的 beforeWrite 作为 beforeOwnedWrite，只由本次选模的鉴权调用，检查捕获的 generation 和重载进行中状态后再捕获最新内存回滚状态，失效时沿用同一个重试错误，不能等 SDK 已改内存/追加历史后才拒绝。SDK setModel 同步发起的首个 checkAuth 才属于本次操作，扩展并发鉴权不触发此 beforeWrite，避免它替尚未提交的请求提前捕获回滚基线。真实 SDK 回归覆盖同/跨身份的 64000 配置鉴权期间 reload 到 96000，以及扩展先切到 C/medium 后旧 B 任务失效：拒绝不得改模型、档位或历史，重试使用 96000。回滚只用于本次 SDK 提交后的失败恢复，不替代同身份路径的先保存再提交。队列出队、鉴权结束及追加 Fast 状态前都调用 assertModelPreferenceWritable，失败不追加回滚记录。集成回归以切换前文件为基线，并在鉴权等待与状态写入边界制造外部写入，实际关闭后重开，验证当前档位与历史档位均保持 high，默认 low 不得落盘。延迟 provider 路径仍在 SDK 创建前按最终目标核对，失配就丢弃该档位，恢复目标模型的启动规则。带归属的推荐不进入初始 scope 档位计算，避免失配后兜底仍残留旧档位。前端本地归属检查不能代替服务端核对，因为其他标签页可能已经修改默认模型。`thinkingLevelExplicit: false` 从前端经过创建客户端、API 一直传到 RPC 启动入口：该档位用于当前会话，但跳过 `persistExplicitStartupPreferences` 的档位参数。手动选择沿用既有持久化行为；手动 `auto` 从草稿的值与来源恢复，重挂载不再触发历史推荐。

同身份重选以应用已保存配置时，`selectRuntimeModel()` 将同步档位写入回调交给 `FastSessionSetting.selectModel()`。调用方从 await 恢复并完成最终同步校验后，在同步替换模型前才通过 `host.captureRuntime` 捕获最新模型和档位；替换与档位限幅/写入之间没有 await。鉴权等待期间扩展已经切模、导致准备阶段拒绝时，不捕获回滚快照，也不恢复更早状态；只有本次替换后的档位写入失败，才恢复提交前的两个内存值，不调用 setter 追加补偿记录，也不提交默认模型缓存。档位在同步提交时读取，保留鉴权等待期间扩展已成功写入的新档位。`lib/rpc-manager-model-config.integration.test.mjs` 覆盖 EIO 后原配置/high 恢复与重试、鉴权期间扩展切模后拒绝重选，以及扩展先改档为 medium 后重选写入失败仍恢复到 medium；历史与运行态必须一致。

显式选模目标只作为本次队列任务的参数传递，类中不保留 targetModel。同身份重选还携带调用方判定时的 expectedModel 引用；显式选模在出队、同身份最终提交前及跨身份鉴权写入守卫处统一调用 assertSelectionRuntimeCurrent，核对 generation 和重载进行中状态：显式选模的旧任务抛出“模型配置已重载，请重试选择模型”，普通 Fast 开关/恢复任务保留直接失效的处理；然后在鉴权、SDK 切模或写入之前比对预期引用，变化就拒绝，不能降级为真正切模。即使 provider/id 相同的新模型引用也按变化处理。显式同身份选模还须在鉴权结束、prepared.validate 通过后再次核对 generation，至写入和提交之间不再 await；引用没变也不能提交 reload 前捕获的配置，各处校验失败共用同一个重试错误消息。真实 SDK 回归以 64000 配置开始鉴权，期间 reload 到 96000，验证旧重选拒绝、原运行态和历史保持不变，重试才应用 96000。Fast 开关、运行时恢复及 available 判断均读取当前会话模型的身份，再通过当前 runtime 目录恢复基础传输参数；失败的重选不能把下一次 Fast 操作导回旧目标。微任务回归覆盖“首次校验仍是 A，SDK 已将 B 的提交排入微任务，await 恢复时已是 B”，必须在落盘前拒绝；同时验证重选拒绝后关闭 Fast 仍保留 B 和其档位，且不新增切回 A 的模型历史。

`reloadRuntime()` 在首次 await 前增加 runtimeReloadsInProgress，finally 中减少；独立 runtimeReloadQueue 串行执行“读取快照、SDK 重载、安装快照”的整个事务，快照读取不能放在队列外。每个任务读完配置后先 assertModelPreferenceWritable，再 syncProjectTrust，最后进入 SDK。RPC 与扩展命令共享 beforeSessionStart：SDK 已完成旧 session_shutdown、使旧 runner 失效并重载资源后，回调先释放 widgets，再删除 extensionStatuses（组件 dispose 也可能设置状态），清理均广播现有 setWidget/setStatus 删除事件；数组和工厂 widget 同样处理，失败重载的页面不能依赖成功后的快照刷新。随后校验存活/磁盘并执行调用方的启动前回调；不能在旧 shutdown 前清理，否则它仍能挂回组件。若资源加载本身失败、启动前回调未执行，则通过旧 runner 的公开 createCommandContext().hasUI getter 检查失效，失效才补清理并继续抛出原错误；不能直接调用 SDK 私有 assertActive。SDK 启动前被拒绝时仍保留有效旧组件。计数包括排队任务，直到最后一个结束才允许显式选模。能力快照回归验证较早请求不能装回过期 Priority。

重载中的实际写入由 `withSessionReloadWriteGuard`（`session-reload-write-guard.ts`）保护：临时包装 manager 的公开 append* 同步入口，在 entry 创建和追加前检查存活/磁盘，包含异步 shutdown/start 钩子恢复后的 pi.appendEntry、消息、名称和标签等记录，不依赖 SDK 私有 _appendEntry。SDK 会捕获钩子异常，守卫因此记住首个冲突并在整个重载返回时重新抛出；本轮冲突后不再接受后续追加。结束后恢复原方法和属性描述符，保留既有持久化隔离包装。ctx.compact 发起的后台压缩不由 SDK 重载等待，因此 wrapper 构造时另用 installSessionCompactionWriteGuard 为公开 appendCompaction 安装 manager 生命周期的检查；临时重载守卫恢复后，这层检查仍在，提交冲突经 SDK 原有 compact 失败路径进入 onError，不追加压缩 entry，也不刷新旧上下文。真实 SDK 集成测试不替换 AgentSession.reload，分别挂起资源加载和启动钩子，验证冲突仍传回调用方；移除扩展的测试覆盖旧 shutdown 新挂组件的释放和旧回调失效。

`ModelRuntimeReloadConflictError`（`model-runtime-reload-conflict.ts`）用稳定 code 和 retryable 标记临时重载冲突。显式用户选模返回错误，由用户重试；启动切模在模型偏好队列之外等待所有 runtime 重载完成，然后重新排队应用原目标，不记录 startupModelSwitchError，也不发送永久 extensions_error。等待方仍跟随原启动 Promise，不能提前用占位模型发消息。每次重试仍复核 modelChoiceRevision，较新成功的手动选模取消旧目标；较新的手动档位也继续优先。非重载冲突沿用原错误处理。

selectRuntimeModel 在模型目录刷新后、查询模型及深度相等提前返回前调用 assertSelectionReady；无变化重选也必须遵守重载边界，结束后仍保持无历史写入。

同身份保留档位与跨身份定档不再用 `if (sameId)` 等源码形状断言验证，改由真实 SDK 集成回归覆盖：会话 high 与全局默认 low 并存；同身份配置重载保持 high，跨身份优先采用目标模型的 medium、无覆盖时沿用 high、不支持推理时限幅为 off，同时检查实际写入的模型及档位记录。

切模期间手选值限幅后，用读取手选值时的修订号提交，reducer 和等待方接受相同结果；此后再发生的手选仍能使旧提交过期。创建等待不设切换次数上限，持续跟随最新任务；`waitForDraftModelSwitchTask` 同时等待当前 Promise 和版本变更通知，`beginDraftModelSwitch` 同步唤醒旧等待方，退出时释放监听；即使旧推荐请求永久挂起，也会立即转向最新任务或读取已提交草稿。连续 25 次被取代的行为测试同时覆盖旧任务结算与永久不结算两种情况。
Saving a default is the star on each row of the model selector and the reasoning menu (pi's Ctrl+S): `PUT /api/models/default` writes `defaultProvider`/`defaultModel` or `defaultThinkingLevel` (`lib/default-preferences.ts`), and the hook also selects that row for the current chat. The route accepts only a model in the resolved `enabledModels` scope, so a saved default always takes effect, and answers `409 { reason: "project-scope", settingsPath }` when the project's `.pi/settings.json` sets a key it would write, since that value wins. The model star marks the resolved `defaultModel`; the reasoning star marks `savedDefaultThinkingLevel`, the raw setting, because the resolved `defaultThinkingLevel` folds in `:level` pins and per-model levels the global write does not change. Both menus render `SelectorRow`; `ModelSelector` shows stars only when given `onSetDefault`, which the subagent profile form does not pass.

The reasoning control stays usable while a run streams: pi-agent-core snapshots `reasoning` when a run starts, but `AgentSession`'s `prepareRequest` / `prepareNextTurnWithContext` re-read `agent.state.thinkingLevel` before every model request, so `set_thinking_level` applies from the next request (the response already streaming keeps its level). `lib/thinking-level-mid-run.integration.test.mjs` pins this; if an SDK upgrade breaks it, disable the control while streaming rather than let it change nothing.

The model selector stays usable while a run streams too, as pi's TUI keeps Ctrl+P / Ctrl+L: `prepareNextTurnWithContext` hands the loop `agent.state.model` before each turn, so `set_model` answers from the run's next request, and the file gets its `model_change` between the run's messages, as in the TUI. Each response's label already names the model that wrote it. Mid-run, `handleModelChange` takes the model and level (a model switch may change it) from `GET /api/agent/[id]` instead of reading the session file, which would replace the run's messages under the stream; the run's end reads it. `lib/model-mid-run.integration.test.mjs` pins the SDK side, with the same fallback.

## Model selector and the mobile keyboard
The keyboard-open CSS keeps the composer's controls row while its model picker is open, so the panel and its focused filter stay (#1271). While open, `ModelSelector` re-reads its trigger's rectangle on viewport resize/scroll and on the root's `style` / `data-keyboard-open` writes (`useViewportHeight` settles WebKit/IME heights with no viewport event), since the shrinking app moves the trigger. Fixed coordinates are the layout viewport's, which the keyboard does not shrink: an upward panel hangs from `top` with `translateY(-100%)`, never a `bottom` derived from `visualViewport.height`, space is measured from `visualViewport.offsetTop`, and an upward panel ends above the keyboard even when its trigger is under it (a Settings field). The re-read always sets a new rectangle: the panel also reads the visual viewport, which can change while the trigger stays put. `e2e/model-selector.mjs` simulates the keyboard; native keyboards remain a real-device check.

## Remote provider catalogs
Built-in model lists are frozen at the pinned SDK version; newer models come from the SDK's pi.dev catalog overlay, which `ModelRuntime.refresh()` persists to `~/.pi/agent/models-store.json` (the pi CLI fills it too) and which restores offline. pi-web's own runtimes only restore it (`allowNetwork: false` / `refreshOnCreate: false`, listed in the header of `lib/model-catalog-refresh.ts`). For remote provider catalogs the network pass runs **only when the user asks** (the "Refresh catalog" button in `EnabledModelsSection` → `/api/models/refresh`), never on a timer or on another request's path, which must not wait on a slow catalog. It calls `refresh()` with `force: true` and never `allowNetwork`, so pi's `PI_OFFLINE` rule holds (`reason: "offline"`), and `shareModelCatalogRefresh()` joins concurrent presses for the same providers. The route returns no model list: a change runs `invalidateModelsCache()` and reloads the panel, whose ordinary `/api/models` load builds a fresh runtime and whose `/api/models/enabled` load refreshes the shared one offline (below); both restore the store.

## llama.cpp router
Pi Web registers the pinned SDK's native llama.cpp provider when it builds the model list, validates a default model, or starts a session with extensions enabled (`llamaCppExtension` in `lib/pi-sdk-internals.ts`). The named built-in honors `-builtin:llama.cpp`. The router-management command `/llama` belongs to the CLI's interactive UI.

Settings › Models › Add provider lists llama.cpp until it is configured (a stored credential or `LLAMA_BASE_URL`); then its row in the sidebar opens the same form. The router URL defaults to pi's `http://127.0.0.1:8080`. Saving the router URL and optional key uses the SDK's login to validate the router before storing its credential in `auth.json`. This user action also refreshes just the router's catalog. Ordinary reads restore the SDK's saved catalog offline. Refresh catalog stays available when the router has no selectable chat models.

## Providers registered at `session_start`
No model listing starts a session: `/api/models` builds a fresh `ModelRuntime` per load, and the Models panel's routes share one (Auth and model config, below). Some extensions register their provider only in the first runtime of a process and defer later registrations to `session_start` (pi-claude-bridge, so a subagent sharing its parent's registry keeps the parent's stream function). Without help their models showed only on the first listing after startup, vanished on a folder switch, and a session could not start on them. `lib/deferred-provider-models.ts` remembers the available models of every runtime pi-web builds (listings, `createModelRuntimeWithExtensions()` and every call of the shared runtime, sessions once their extensions are bound) and adds back the models of providers a runtime **does not register at all**; a provider it registered but cannot use (signed out) is never added. `startRpcSession()` builds a session whose requested or restored model is such a deferred one on the default model, then switches to it with `set_model` once `session_start` has run, as the binding's last step (`afterSessionStart`), so whatever waits for the binding sees the switched model and a `session_start` dialog does not hold the start (#1678). Until then a model or level picked meanwhile stands (`pendingStartupModel()`), a tool change that rebuilds the session rebuilds on the target (`startupModel()`), and a wrapper already closing skips the switch; with no usable model requested, likewise for the pick `/api/models` pre-selects (the default when in scope, #1240). After the switch it sets the thinking level pi's `createAgentSession` gives that model at startup (a resumed session's saved level; a new one's requested level, `enabledModels` pin or `modelThinkingLevels` entry; then `defaultThinkingLevel`, else `medium`): `set_model` alone falls back to the stand-in model's level. A project-only extension that defers its provider would also appear in other folders' listings; picking it there leaves the session on its default model.

Only models from `ModelRuntime.getRegisteredProviderIds()` (extension `registerProvider` / native provider registrations) and virtual models enter that remembered catalog. Virtual-only providers are absent from that registration list; a model must still exist in `getModel()` and have no `getPhysicalModel()` counterpart to qualify. Absence from both means a concurrent refresh may have removed a physical model while availability loaded. Built-in and models.json-only physical models come from the current runtime, so deleting or renaming a custom provider cannot add its old id back, even if an open session later reports its pre-save runtime. Clearing the whole remembered catalog on Save would lose the deferred extension registrations it exists to preserve.

## `enabledModels` scoping
`enabledModels` uses pi's `--models` syntax: minimatch globs against `provider/modelId` or a bare `modelId`, fuzzy matching for non-glob patterns, an optional `:thinkingLevel` suffix. Never compare patterns as strings: `lib/model-scope.ts` delegates to the SDK's `resolveModelScopeWithDiagnostics()` so pi-web and the TUI agree, and falls back to every available model when the patterns resolve to nothing. A bare id several providers offer is not refused: pi (1.3, #10160) scopes every one of them and warns that the entry is ambiguous, which reaches the composer as a `modelScopeWarnings` line, and the Models panel shows each of them on (switching one off rewrites the entry to the other's `provider/id`). `startRpcSession()` resolves the scope before creating an AgentSession and passes the initial model, thinking pin and SDK-native `scopedModels` atomically; `GET /api/models` uses the helper only for selector data, `thinkingLevelPins` and `modelScopeWarnings`.

The selector lists models in pi's `/model` order (`orderSelectorModels()`): a scope in `enabledModels` order, otherwise sorted by provider id only, so a models.json provider keeps its file's order (#783). `ModelSelector` groups by provider in first-appearance order and never re-sorts; never sort by name in the route or the client. Model rows show the models.json `name` and fall back to the id, here and in the Models panel's sidebar (`modelSidebarLabel()`); the id is fixed by the provider and often hard to read (#885). Each `modelList` row also carries the provider's display name from `ModelRuntime.getProviders()` (`providerName`, falling back to the id): group headings use it, with the id kept as the heading's tooltip, and the filter matches it. The Models panel sidebar labels a custom provider by its models.json `name`, then the runtime name, then the id (`providerSidebarLabel()`), so it no longer shows a readable provider as a raw id. The runtime names come from `/api/auth/providers`' `providerNames`, which covers every registered provider, including classifier-only built-ins with no chat models (e.g. TypeSafe); the enabled-models view only knows providers with chat models. The custom provider panel's Display name field, under the Provider ID field (which renames the key), edits that `name` in the draft (`setProviderDisplayName()`; blank removes it; the placeholder shows the id, though a built-in id's entry falls back to pi's built-in name once saved) (#1567). An extension's provider name wins over models.json's in pi, so the selector keeps it whatever the field says. pi reports a saved `name` as the provider's runtime name, so the label skips a runtime name equal to the saved `name` (`providerRuntimeName()`), and a save refetches `providerNames` and replaces the saved names only once that refetch lands (before it, the old runtime name still equals the old saved name; otherwise a cleared name would come back as the label). An entry left with only overrides by clearing a saved `name` stays a custom provider until that save, so the panel doesn't jump to the managed provider mid-edit. Managed providers' panels have no such field: a `name` would turn their overrides-only entry into a custom one. With a scope active (`isScoped`), `ModelSelector` has pi's `/model` `scoped | all` row, starting on scoped (Tab on the filter, or a tap); `useAgentSession` fetches `GET /api/models?scope=all` only on switching to all or when the shown model lies outside the scope, and merges its names and reasoning levels into the maps (each `loadModels` drops them and the list). A model picked there is a session choice like any other (`set_model`, or the new session's start model, as pi's `--model` outside `--models`; `selectInitialModelScope()`'s `availableModels`); `scopedModels` stay as they are and nothing is written to `settings.json`. Rows outside the scope get no default star.

The Models panel edits it only through `/api/models/enabled`, never with patterns composed in the browser. Every toggle is a **minimal edit** (`lib/enabled-models.ts`, ADR 0004): an unmatched pattern stays verbatim, only the pattern covering a switched-off model is expanded in place (keeping its `:level`), and a fully enabled provider with two or more entries collapses into one glob (an enumerated list rots when a catalog renames a model); a lone exact reference stays. Never rewrite the whole list from `getAvailable()` like the TUI's `/scoped-models`: it sees only providers passing `checkAuth()` right now, so it would drop a signed-out provider's entries and flatten globs and pins. **Never assume `provider/*` covers a provider**: minimatch's `*` stops at `/`, missing nested ids (`commandcode/sakana/fugu-ultra`, most OpenRouter ids); `resolveProviderGlobs()` keeps `provider/*` or `provider/**` only when it matches exactly the provider's models, else writes the provider model by model.

- Switching off the last enabled model is refused, `409 { reason: "last-model" }`: an empty scope means every model.
- Writes go to the global settings file only. A project `.pi/settings.json` `enabledModels` replaces the global array, so the route reports `scope: "project"` and the switches are read-only. The route returns the deciding file as `settingsPath`, which the banner names with the count (`~/.pi/agent/settings.json · enabledModels 20/104`).
- Built-in and extension-registered providers get per-model switches; a models.json provider gets one `EnabledModelsProviderSwitch` in its detail header beside Delete (ADR 0004), on only while all its models are on, so a partial selection reads off beside the sidebar's `1/2` and one click completes it. Why a switch cannot move (the last enabled models, a project scope, the provider missing from the runtime) is the note under the detail header (`EnabledModelsProviderSwitchNote`), which the switch points at with `aria-describedby`; a built-in provider's rows and Disable all point at the section's scope and last-model notes likewise. A tooltip alone never shows on a touch screen ([settings-ui.md](settings-ui.md); ADR 0004 records the change).
- A models.json provider missing from the runtime (unsaved edits, no models, a key that does not work) is never reported as a sign-in problem: its switch is disabled with that note, while `EnabledModelsSection` (built-in providers only) keeps the sign-in empty state.
- `op: "prune"` is the only operation that drops unmatched entries (cleanup after a catalog rename); `op: "clear"` removes the setting; every other operation preserves them. Unmatched means matching no available model, a signed-out provider's entries included, as in pi's own `No models match pattern` warnings. #1427 kept those on prune so signing back in restored them; that left a provider removed for good (`openai-codex` after Sign in with ChatGPT) with entries the panel lists no switch for and the button would not delete, so they are pruned like any other and the button's hint says signing back in will not restore them.
- Saving models.json calls `op: "resync"`, the only operation that repairs entries (a toggle never touches what the user did not switch): it rewrites renamed models, then renamed providers (model references still spell the old provider id), cuts back entries whose provider prefix no longer scopes them, and re-asserts providers fully enabled before the save. Otherwise a rename corrupts the scope: pi also matches the bare `modelId`, so a provider renamed to `stepfun` makes `stepfun/*` enable `commandcode`'s `stepfun/Step-5-Preview`; a model renamed to an id with a slash leaves `provider/*`; a renamed sole entry resolves to nothing, i.e. every model. `ModelsConfig` must mirror every draft array move in `savedModelIdsRef` so `collectModelRenames()` can tell a rename from an add or a delete, and every provider move or deletion through `renameProviderEntry()` / `deleteProviderEntry()` so a deleted provider's pending rename is forgotten and a new provider taking a freed id is not mistaken for the saved one.

## Ordering models.json models
On a desktop a custom provider's model row is dragged onto another row of the same provider (native HTML5 drag and drop, as the right panel's tabs: no grip, no pointer handling of our own, the browser scrolls the list at its edges; a drop line shows above or below the row, none where the order would not change). Alt+↑/↓ on the focused row is the keyboard path. Touch gets no reordering on purpose (iOS never starts a native drag); A–Z beside + Model works everywhere and sorts that provider once by `modelSidebarLabel()`, with natural, case-insensitive comparison and stable ties. `modelDropIndex()` turns "before/after row N" into the final slot. `moveModelEntry()` / `sortModelEntries()` change only that provider's draft array and move `savedModelIdsRef` with it, so a later rename is not mistaken for a move; the selection follows its model's old slot through the returned order. Row keys follow the model object (`modelKeysRef`), so the focused row stays mounted as it moves; `updateModel()` hands the key to the edited object, so typing in the detail pane does not remount the row. Save writes the array through the existing models.json path, and later additions still append. There is no custom drag handling, persistent sort preference or separate display order, and explicitly enumerated `enabledModels` scopes keep their own order.

## Context-window overrides
Each model row of a managed provider (`EnabledModelsSection` given `contextSettings`) carries one compact text field, `ModelContextWindow`, editing `providers[provider].modelOverrides[modelId].contextWindow` in the **same models.json draft** as custom models; the shared Save writes it. The row keeps its one-line height: no visible label (an `aria-label` names the model, a `title` says tokens), no Default button, no current-value line; one note above the list says what the fields are; the shared footer says how open sessions apply saved model edits. The placeholder is the window pi resolves for the model (the enabled-models view's `contextWindow`, from the SDK-resolved model, overrides included), so a blank field means no override. It reads the saved file, not the draft: a cleared override still shows its old value until Save. Clearing the field removes only `contextWindow`, pruning empty containers while preserving credentials and other overrides. An overrides-only entry stays under its managed provider rather than appearing again as a custom provider; it is listed as custom only once `/api/auth/providers` has answered without that provider (a failed request counts), so it does not flash there while the lists load. The detail pane opens the custom-provider form only for an entry that list shows, so a first or remembered selection of such an entry stays blank until the lists answer and it moves to its managed provider.

Save (client, then the route) checks every override with `parseContextWindow()`: text typed in the field must be a whole token count, while a number already in the file only has to pass pi's own check (`exclusiveMinimum: 0`, so `400000.5` loads), or one hand-edited value would block every unrelated save. A value pi refuses (`0`, `null`, a non-numeric string) is refused with the model's `provider/id`: pi drops the whole models.json on a schema error. An invalid draft stays visible, marked `aria-invalid`, and the footer names the model.

New runtimes pick up the saved budget; a loaded session picks it up when its model is selected again (below). Pi's `/reload` (1.2 through 1.4) reloads resources but retains the session's model metadata, so do not promise that it applies this edit. This changes Pi's context accounting, not the provider's actual limit; `enabledModels` switches still save separately and immediately.

## Applying saved model edits to open sessions
A session binds a model object; saving models.json does not touch it (#1273). As pi's `/model`, which refreshes the runtime before listing, `set_model` refreshes the chosen provider (`allowNetwork: false`, `providers: [provider]`, 15 s) before looking the id up, even for an id it already has, and the live composer's `ModelSelector` sends `set_model` for its already-selected row (`onReselect`; draft selectors keep that click a no-op). A failed or timed-out refresh keeps the cached definitions, as the TUI does. An unchanged definition is not bound again (no `model_change` entry, no `model_select`); a same-id edit keeps the session's thinking level, which the SDK clamps to the new capabilities. 切到另一个模型时，`selectRuntimeModel` 会按 `applyModelDefaultThinking` 重新落一次强度：`settings.json` 的 `modelThinkingLevels` 里有这个模型就按它（SDK 已经应用，不再覆盖），否则 `enabledModels` 的 `:level` pin → 这个模型最近 10 次用过的众数（`lib/thinking-level-preferences.ts`）→ 切换前的档位，最后由 SDK 限幅到新模型支持的列表。界面不自己推算，等 reload / 实时快照读回结果；还没创建的新会话由 `useModelSelection` 用同一套规则（pin → 众数 → 旧档位限幅）算出创建时要带上的档位。草稿的这次解析是异步的：整个切模是一个可等待的任务（`draftModelSwitchRef`），首条消息（`handleSend`）和 materialize（`ensureNewSession`）都先等它，否则会拿新模型配旧档位创建会话。等完再去读最新的草稿设置（`currentNewSessionSettings()`），不能沿用渲染闭包里的 `newSessionModel`，也不能只读本实例的 ref：发送前刚切过模型时闭包里还是上一个，等待期间切走再回来时模型甚至是在另一个实例里选的（materialized 分支补发的 `set_model` 会把已经切好的运行时又切回去）。`ensureNewSession` 的等待必须排在 `START`/`RETRY` 之前，因为状态机进入 `materializing` 后不再接受档位事件，在途结果会被丢掉。解析出的模型和档位用一次 `SET_MODEL`（带 `thinkingLevel` + `thinkingLevelSource`）提交：分两次写会留下一段「新模型 + 旧档位」的窗口，用户正好在窗口里切走再回来，重建的组件就会把旧档位套到新模型上。来源也要持久化——`manual`（用户点选）填回 `thinkingLevelOverrideRef`，`auto`（切模解析出来的推荐）填回 `recommendedThinkingLevelRef`，否则自动推荐在重新打开草稿后会变成显式选择的档位。切走再回来重建的是另一个实例：它在后台解析完档位后把模型和档位一起写进草稿状态，本实例在没有在途切换时跟进这份值（`newSessionModelOverrideRef` 与两个档位 ref `awaitDraftModelSwitch()` 采用结果前都核对 `isLatestDraftModelSwitch`，否则旧实例晚结算时会把用户后来选的模型写回草稿（登记与清理只按身份比较，管不住提交顺序）。`awaitDraftModelSwitch()` 两处都查，拿到结果后直接写进本实例（状态更新可能还没进入这次 render）。切模期间用户手动选档会让推荐请求过期（`committed: false`）：这时不能整段放弃，模型仍要提交，档位用用户刚选的那一档，否则草稿只留下档位、模型还停在上一个；只有被另一次切换取代时才什么都不写。创建参数（模型、档位、`desiredShadowMindEnabled`、`toolNames`、请求身份）要在等完之后按最新草稿取：等待期间用户还能改模型、档位和 Shadow 开关，把工具预设从完整改成只读，而且这些改动往往是在切走再回来重建的那个实例里做的——本实例的 props 与 refs 都停在离开那一刻，照它们创建就会用上已经被取代的旧模型和旧名单。草稿设置因此另有一份渲染无关的镜像（`lib/pending-new-session-mirror.ts`）：`dispatchPending` 写它，并且**用它当归约的输入**——React state 的提交时机不确定，切模任务结算与它同在一个微任务链里，按 state 归约可能接在还没提交的上一份后面。`currentNewSessionSettings()` 按 cwd 从镜像取模型、档位与 Shadow，`currentNewSessionToolNames()` 也读草稿自己记下的 `tools`（`SET_TOOLS` 在用户选择工具档位时写入），浏览器偏好只用来初始化一个从没改过工具的草稿——偏好是整台浏览器共用的一份，别的标签页改它、或者写入被拒（隐私模式、配额）时，输入框显示的档位和创建请求用的名单就会分叉。这一份档位还要按**目标模型**限幅：切模等待期间输入框仍按切之前的模型给选项，A 支持 `max` 而 B 最高只到 `high` 时，手动选的 `max` 保留下来会把 B 做不到的值写进草稿。`handleModelChange` 在保留手选值时用 `clampThinkingLevelToSupported` 折中（`thinkingLevelsRef` 按 `provider:modelId` 查），`currentNewSessionSettings()` 再兜一次；两者都交给等待方同一份结果。默认模型的推荐档也要进草稿：`loadModels` 把 `load()` 算出的推荐写进 `recommendedThinkingLevelRef` 的同时，若草稿仍是初始 `auto`（`thinkingLevelSource` 不是 `manual`，用户主动选的 `auto` 表示交给服务端，`explicitAutoThinkingRef` 还让 `applyPinnedThinking` 不再把它算成需要推荐的草稿）就 `SET_THINKING_LEVEL(…, "auto")`，否则创建请求省掉 `thinkingLevel`，服务端按 settings 的默认档位开跑，历史推荐与默认档位不同时首条消息用的档位和界面显示的不是一个。`awaitDraftModelSwitch()` 的等待不设两三轮的短上限：每一轮都在结算前被下一轮取代时提前返回，会让创建带着还没结算的那次选择进入 `materializing`，它后来的 `SET_MODEL` 被状态机丢掉。建好会话或丢弃草稿时镜像与 state 一起删，否则下一个草稿会从上一份记录继续。materialize 和首条消息两个入口都这样取值；等的时候另一个入口已经把 runtime 建好时直接接管，不重复创建。切模期间的手动改档也可能发生在另一个实例里，本实例的 `thinkingChoiceRevisionRef` 看不到：`SET_MODEL` 因此带上发起时的 `levelRevisionAtStart`，与草稿当前的 `levelRevision`（只有 `source: "manual"` 的 `SET_THINKING_LEVEL` 推进，目录刷新带来的自动推荐不推进）对不上时 reducer 只提交模型、保留那一档；`handleModelChange` 同时把交回给等待方的结果换成草稿里的那一档，否则选择器会被写回推荐值。反方向同理：`load()` 只按默认模型算推荐，草稿选了别的模型时不再套用（改动前后都按 `newSessionModelRef` 核对模型），否则会把默认模型的档位写到目标模型的首发请求上。目录刷新和切模推荐各走各的 gate 通道（`thinking-default` / `thinking-switch`）：刷新会重新开始自己的通道，但不再把在途的切模推荐作废——否则切模会退回用上一个模型的档位提交，把 `max` 存到只支持 `high` 的模型上。切模的三种结果要分开处理（`ThinkingSwitchOutcome`）：`applied` 用推荐值，`manual`（用户在这次切换期间手动改了档，按 `thinkingChoiceRevisionRef` 判断，目录刷新不会推进它）保留用户刚选的那一档，`superseded`（同一草稿上起了更新的一轮）才整段放弃。已有运行时的暂存会话读回档位时还要看快照是否被采纳：`applyRuntimeSnapshot` 返回 `{ thinking }`，快照早于用户刚改的档位时它会被跳过，切模结果不能再用它的档位覆盖选择器。默认档位的加载同理：`load()` 被切模型取代时返回 `undefined`，这时不能拿它当"没有推荐"去清 `recommendedThinkingLevelRef`，否则界面还显示着推荐档、创建请求却省掉了 `thinkingLevel`。反方向也一样：草稿已经有档位（用户挑的或切模型解析出来的）时，`loadModels` 不再让 `load()` 按**默认模型**算一遍推荐（`applyPinnedThinking` 现在同时要求两个 ref 都为空）——草稿选的往往是另一个模型，用默认模型的推荐覆盖它，界面会跳回一个用户没选过的档位。两种键格式不能混用：pin 用 `provider/modelId`，支持档位表（`thinkingLevels`）用 `provider:modelId`，查错键等于没限幅。新会话内部仍是 `auto` 时，选择器显示的是 settings model, matching pi.

## Auth and model config
- `ModelsConfig` combines `~/.pi/agent/models.json` with provider auth status from pi's `ModelRuntime` (`/api/auth/providers`).
- **One extension-loaded runtime per agent dir** serves `/api/auth/providers`, `/api/models/enabled`, the logout and API-key provider lookups and MCP Test's provider token (`getModelRuntimeWithExtensions()`, `lib/model-runtime.ts`; #1226). Building one runs every extension at cwd = agent dir, and the SDK's extension factory cache holds one cwd, so a build per request re-imported every extension between two of a project's session starts and blocked the event loop meanwhile (two per Settings › Models open, one per switch or auth action). Only the registrations are reused: every call runs `refresh({ allowNetwork: false })` and `rememberProviderModels()`, which read auth.json, models.json and models-store.json again, so auth status is as fresh as a new runtime's. The calls refresh one at a time, each after it was asked (`serializeByKey()`): when two refreshes overlap, the SDK keeps only the later availability pass and the earlier caller returned the status from before both (Settings asks for the lists and the switches at once, so a key just saved read as missing). Each call awaits the build before it joins that queue, and each built runtime has a queue of its own: the SDK awaits extension factories, and extension providers' `refreshModels()` in an offline refresh, with no timeout, so one stuck there would otherwise hold every later call, even after invalidation. A plugin change (every `POST /api/plugins`, also a failed one: an update can fail halfway) and a session's `reload` or an extension's `ctx.reload()` drop the entry (`invalidateModelRuntimeWithExtensions()`), and a failed build is not kept. An in-place plugin update keeps the package's path, so while the SDK's factory cache sits at the agent dir the rebuild reuses the old factory: the update shows after `/reload`, or once a session start in a project has moved that cache, when the entry is next built (at the latest when it expires). The entry also lasts at most an hour from the end of its build, only a backstop for what no event announces: changes made outside Pi Web (`pi install` from a terminal, an edited extension file), an extension that failed to load, a refresh stuck in an extension provider. It was 10 minutes until #1465 (13 s on the first request after an idle spell, with 11 extensions). Only rarer, not gone: moving the build to the background still stalls every request while it imports, since imports are synchronous, and dropping the timer loses those recoveries. A build still evicts a project's cached factories once (upstream earendil-works/pi#10911 was closed). The OAuth login stream and the catalog refresh still build their own (`createModelRuntimeWithExtensions()`): `login()` and a network `refresh()` change the runtime they run on, for seconds.
- Keep an omitted provider `api` unset in the editor and discovery request: pi resolves the protocol for built-in providers. Opening a provider must not persist a guessed protocol. New custom providers still start with an explicit `openai-completions` default.
- Save (the panel, then `PUT /api/models-config` with a 400) refuses a provider entry pi rejects on its own (`checkProviderEntries()`, `lib/model-provider-check.ts`): one with none of a Base URL, a model, headers, compat, an API key, `authHeader` or a non-empty `modelOverrides` (Add provider's untouched stub, #1353), or `oauth` without a Base URL. pi drops just that provider and shows its error in every chat's model banner. The panel names the provider and selects it, so an entry already on disk is filled in or deleted from the UI; never drop it silently. An empty `modelOverrides` is not an overrides-only entry (`isOverridesOnly()`): it would hide under its managed provider's page, which has no Delete. Rules that depend on pi's catalog (a custom model inheriting a built-in provider's Base URL or API) stay pi's to report: replaying them would copy SDK internals and could refuse a provider an extension registers.
- Provider listing is capability-driven, never id-driven: `lib/provider-listing.ts` decides membership from `auth.apiKey.login` / `auth.oauth` plus the stored credential type, so a dual-auth provider (anthropic, github-copilot and others; the set changes between SDK releases) appears exactly once. `lib/provider-listing-runtime.ts` adapts `ModelRuntime` to it.
- auth.json holds **one** credential per provider and `ModelRuntime.logout()` deletes whichever it is, so the delete routes use `removeStoredCredentialIfType()`, which compares and deletes under pi's auth-file lock. After any auth change `ModelsConfig` refreshes *both* provider lists, or a dual-auth provider renders twice.
- OAuth/device-code/manual-code flows stream from `GET /api/auth/login/[provider]`; a manual code POSTs back with a short-lived token kept in `globalThis.__piLoginCallbacks`. `login()` gets pi's `LoginOptions` as the TUI passes them (`createLoginOptions()`, `lib/model-runtime.ts`): Sign in with ChatGPT, the `openai` provider's OAuth, fails at once without `getDeviceId`, which reads or creates `deviceId` in the global settings.json, the same one the TUI uses. pi names `openai-codex` "OpenAI Codex (legacy)" since that login supersedes it, so its friendlier label keeps "(legacy)". Closing the stream (the panel's Cancel, closing Settings, a dropped connection) aborts `login()`, as Esc in the TUI's login dialog does; a device-code poll left running would sign the provider in after a Cancel. An extension can still report progress from a timer after that or after login settles: `send()` drops it once the stream is closed, since an enqueue on the closed controller throws outside any await (an uncaughtException in the server log).
- API-key routes store and remove keys through `lib/provider-credential-store.ts` (`storeProviderCredential()` / `removeStoredCredentialIfType()`), not `AuthStorage`, and never through `ModelRuntime.login()`, which runs an unbounded catalog refresh. Status endpoints never return the raw key.
- The model test route is `app/api/models-config/test/route.ts`; `app/api/models/test/` does not exist. Its probe goes through `modelRuntime.completeSimple()` with a fresh `sessionId`, as a chat does, never `@earendil-works/pi-ai/compat`, which skips the runtime's request preparation: auth (API key, OAuth, auth `baseUrl`), models.json headers and gateway headers such as OpenCode's `x-opencode-session` (opencode.ai answers 400 `MissingSessionID` without it).
- A custom model's Advanced settings edit native `models[].baseUrl` (pi has no `modelOverrides` equivalent). Blank removes the key, so the model inherits the provider URL again; `api` and `baseUrl` inherit independently. The field only trims whitespace, never adds `/v1`. Catalog matching uses the effective URL. Test sends the whole draft model, so any edit clears its result and a request id drops replies for an older draft.
- A custom model's Advanced settings edit pi's `inputLimits.images.resize.maxBytes` as **Image size limit (bytes)** (`lib/model-image-limits.ts`), shown while the model takes images or already sets it. pi resizes or recompresses a new image (attachment, read result, tool-result image) until its base64 payload is under it, default 4.5 MiB; history is never re-encoded. Blank removes the key and prunes the containers it leaves empty, keeping the other `inputLimits`. pi's schema wants an integer of at least 1 and a failure drops the whole models.json, so text that is not one stays a string in the draft (marked `aria-invalid`) and Save, client then route, refuses it naming `provider/id` (`checkImageMaxBytes()`). Managed models have no field yet (`modelOverrides` accepts `inputLimits` too).
- A models.json model on `anthropic-messages` (its own `api`, else its provider's) gets **Claude adaptive thinking** under Advanced settings › Compatibility, which writes pi's `compat.forceAdaptiveThinking` (built-in Claude 4.6+ models set it in generated metadata; pi never infers it from a custom model's id). Without it pi sends `thinking.type: "enabled"` with a token budget (`xhigh` and `max` clamp to high's 16384). Claude Opus 5.5 through a gateway answered that with an empty thinking block and no bytes at all until the answer began, so minutes of silent thinking ended in `terminated`; adaptive thinking streams the summary. Switching it off removes the model's key, or writes `false` when the provider's `compat` turns it on.
- Fetch models (`lib/model-discovery.ts`) copies only capability fields whose meaning does not vary between gateways into the added entries: `contextWindow`, `maxTokens`, `reasoning: true`, `input` from `modalities.input` (or a bare `input` array) limited to the modalities pi knows (`text`, `image`; `["image"]` stays as advertised), and a `thinkingLevelMap` from an advertised effort list (`supported_efforts`, `supportedEfforts`, `reasoning_levels`; levels the list omits become `null`, `max` / `xhigh` only when mapped, and `off` stays unmapped even when the list names `none`). Ambiguous fields (`max_tokens`, `default_effort`) and junk values are dropped (#856). So is `pricing`: the same names mean different units at different gateways (Vercel AI Gateway quotes `input` / `output` per token, Chutes `prompt` / `completion` per million), and a guessed unit is off by a million in every message's recorded cost; prices come from Fill model details (models.dev, `lib/model-catalog.ts`), which fills only empty keys.
- `models.json` may be a symbolic link (a dotfiles setup). The atomic write renames a temp file over the destination path, which replaces the link itself and leaves its target holding the old contents, so `writeModelsConfig` writes through `realpathSync()` to the target and the link survives. A dangling link is refused (`ModelsConfigReadError`, 409) instead of replaced: the read guard reports it as missing, and replacing it would silently break the user's link. pi itself never writes models.json. Of the other agent-directory writers, the global mcp.json writer resolves links on its own (and creates a dangling link's target), settings.json is written in place so its link survives, while subagent profiles and `agents/settings.json` (`writePrivateFileAtomicSync()` too) still replace a link.
