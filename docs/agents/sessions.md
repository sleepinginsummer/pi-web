# Sessions, branching and live events

## AgentSession lifecycle (`lib/rpc-manager.ts`)
- One `AgentSessionWrapper` per session id in `globalThis.__piSessions` (`globalThis` survives Next.js hot reload; a module-level Map does not). Concurrent `startRpcSession()` calls share one start Promise (`globalThis.__piStartLocks`). Idle timeout: 10 minutes (`PI_WEB_IDLE_TIMEOUT_MS`, `0` disables).
- Stop cannot cancel a run awaiting a promise that ignores the abort signal (a third-party extension handler or tool): `inner.abort()` never returns. So Stop (`abort`, `abort_bash`) sets `forceShutdownOnIdle` and arms the idle timer, shutting the wrapper down one idle timeout after the first Stop even while it runs. Later commands (a reload's `get_tools`, Stop again) must not push that deadline back; with `PI_WEB_IDLE_TIMEOUT_MS=0` it still arms, at 10 minutes.
- **A wrapper is closing from the moment `shutdown()` or `destroy()` starts**: `isAlive()` turns false at once, so routes stop sending it commands, but `startRpcSession()` builds the replacement only once it has disposed (`closingRpcSessionWait()`, at most the shutdown deadline plus 1 s). Until then it owns the session: an extension's `session_shutdown` may append to the file, and `dispose()` releases provider resources (a Codex websocket) by session id. `setRpcSessionTools()` waits likewise for a closing wrapper or a start under way, then applies the selection to the resulting wrapper, never through a second `SessionManager`. A stuck run counts as busy (`isRunning()`) until disposal.
- The closing wrapper stays in `__piSessions` until disposed or replaced; its `onDestroy` removes the entry only while it still points at that wrapper, or a late cleanup would unregister the replacement. `registerRpcWrapper()` clears the callback of the entry it replaces (a pre-hot-reload wrapper still deletes by id).
- Extensions get `PI_WEB_SHUTDOWN_DEADLINE_MS` (5 s; `0` or invalid keeps the default) for `session_shutdown`, then the wrapper logs once and disposes anyway: closing an MCP connection has no upper bound. Extension binding is awaited first, without a deadline.

## 初始化等待与重试（`lib/rpc-manager.ts`）

- 后台延迟切模和 provider 目录发现使用 `whenExtensionsBound()`，跟随实际审批/绑定 Promise，不继承请求期限。`waitUntilReady()`、`waitForStartupModelSwitch()` 的请求等待默认 20 秒，超时只拒绝本次调用，后台仍继续执行，`extensionsInitializing` 保持真实进度；只有实际绑定或切模失败才记录 `extensionsError`。
- `trackStartupModelSwitch()` 保留初始化操作；显式 `finalize-existing` 可重做真实失败的目标模型切换，并发请求共享在途任务。请求超时后的重试加入原任务，不能创建第二个 runtime，也不能静默使用占位模型。测试通过真实 SDK 审批、客户端两阶段创建和路由验证“超时后批准，再重试 ready”以及 provider 恢复后的并发重试。

- 启动模型/强度与手动偏好通过同一 wrapper 队列提交。成功手动选模废弃旧目标与旧错误回写，失败的手动选择不取消初始化；仅手动调整强度仍完成原目标模型初始化，并重新应用用户请求的强度（而非占位模型限幅后的等级）。模型与强度分别跟踪选择版本，避免旧任务越过较新的用户选择。回归覆盖审批后目标可用/缺失、执行中切换成功/失败、独立强度选择和手动选模失败。

## Fork never touches the running AgentSession
Never fork through `AgentSession.fork()` / `AgentSessionRuntime.fork()`: they replace the session in place (`inner.sessionId` becomes the new id; the current run is aborted first), so a wrapper registered under the old id would serve the forked state and corrupt the `parentSession` chain.

`send("fork")` / `send("fork_branch")` open a separate `SessionManager` on the source file and `createBranchedSession()` from it. So forking works **while the source runs** (only a running `!` shell command refuses): pi appends each finished entry synchronously in this process, and the in-flight assistant message lands after the fork point. A source with no file yet is refused with the upstream "has not been saved yet" wording. After a `fork` (never `fork_branch`) an idle source is shut down, since the browser moves to the child; a running one keeps its run and its running row. `clone` refuses a running session: it copies the current branch, which is the run in progress.

## In-session branching waits for the run
pi's `navigateTree()` refuses while streaming or compacting: the file has one leaf pointer that the run appends under, and navigating swaps the agent's context. So "Edit from here" is hidden while busy, the BranchNavigator renders read-only (`locked`) with a note, and `handleLeafChange` refuses (switching only the view would show the live run under another branch). To branch from a running session, fork it.

## Two kinds of branching — don't confuse them
- **Fork** ("New session" on a user message): a new `.jsonl` file, shown as a child in the sidebar via the `parentSession` header field.
- **In-session branch** ("Edit from here" / BranchNavigator): `navigate_tree` within one file; entries share a `parentId`. Switching calls `/api/sessions/[id]/context?leafId=`.

## Session files can be fully rewritten
`parentSession` in the header is **display metadata only**, so rewriting the whole file with `writeFileSync` is safe (pi does it in migrations); cascade-reparenting children on delete relies on this.

## ToolCall field normalization
Pi stores `{type:"toolCall", id, name, arguments}`; `ToolCallContent` uses `{toolCallId, toolName, input}`. `normalizeToolCalls()` (`lib/normalize.ts`) converts in both `session-reader.ts` (file load) and `handleAgentEvent` (`hooks/useAgentSession.ts`, streaming).

## Provider signatures in browser messages

Browser display copies omit content-block `thinkingSignature`, `textSignature`, and `thoughtSignature` through `lib/message-signatures.ts`. OpenAI reasoning signatures can contain `encrypted_content` needed for model continuation. `entryToUiMessage()` covers history and context pages; `projectTreeForResponse()` covers full navigation trees; `toClientAgentEvent()` covers assistant starts/ends and standalone tool calls. Reconnect snapshots pass through that event projection, while snapshot deduplication compares the original SDK message reference. The projection copies signed assistant messages and blocks, preserving visible content, display flags, and nested tool arguments. SDK state, persisted sessions, forks, and the raw entries embedded in HTML/JSONL exports retain their provider signatures for restoration and continuation.

## SSE reconnect on page refresh mid-stream
On mount `useAgentSession` loads the history, then `GET /api/sessions/[id]/state` (`loadSession(…, includeState)`): `state.isStreaming` or `state.isPromptRunning` resumes the run in the UI, and `thinkingLevel` / `isCompacting` sync from it. No reconnect is needed: the selected session's stream stays open whether or not it runs (`maintainEventsConnected()`, warm-session effect), and its `connected` event carries `isStreaming`.

## Compaction SSE events
`handleAgentEvent` accepts `compaction_start` / `compaction_end` and the older `auto_compaction_*` pair to keep `isCompacting` in sync. Manual compact is a blocking POST: `isCompacting` holds until it returns, the button meanwhile Stop compaction (`abort_compaction`). When a run ends, Compact (and the tools button) take the spot Stop held left of the sound toggle, so `ChatInput` ignores pointer clicks on them for `RUN_END_CLICK_GUARD_MS` (600 ms) after it: the second click of a double click on Stop otherwise started a compaction nobody confirmed (#1131). Keyboard activation (`detail` 0) and Stop compaction are never held back.

## Process details start open without an answer (`ProcessDetailsGroup`, `components/ChatWindow.tsx`)
A grouped turn's Process details start collapsed only when the answer shown under them has text or an image (`collapsesProcessDetails()`, `lib/message-display.ts`). A turn that ends on an error or truncation notice alone, e.g. empty `stopReason: "error"` replies after text and a trailing tool call, still shows that notice but keeps them open: the earlier text is inside them (#906). The group is keyed on this decision, so a leaf switch that changes it resets the group; a search hit inside opens it (`reveal`).

## Turn duration (`lib/turn-duration.ts`)
A finished turn's length is the time from its anchor to the end of its last response or tool result (a response ends at its request `timestamp` plus the `durationMs` pi records since 1.1). It is wall-clock time, so a tool waiting on the user counts; only the wait between an answer and a run an extension started after it (`sendMessage` with `triggerTurn`, as pi's file-trigger example: its custom message is no anchor, so the run stays in the turn) is left out. It shows on the Process details line, or under the answer when the turn has no process details; a turn whose last response has no `durationMs` (an older session) shows nothing. The Process details line stays one line: the button's `maxWidth` lets its span's ellipsis cut the line at the column; without it a phone (320 to 375 px) ran the longer line past the gutter and clipped it at the screen's edge. A running turn shows no time, as in pi's TUI: a live timer would compare the browser's clock with pi's.
Both ends of the subtraction must be pi's times, and the browser's clock can differ (a phone on the LAN). The bubble a send shows at once is stamped in the browser and stays until the reload after the run (the delivered user message replaces it only when the two differ, `userMessageKey()`; an extension command's `/name` has none), so a turn is timed only when its anchor has an entry id (`entryIds`), which only messages read from the session file carry: from a run's end until that reload (`loadSession` at `prompt_done` / `agent_settled`), the turn shows no time rather than one taken across two clocks.

## Compaction summary card (`CompactionMessageView`, `components/MessageView.tsx`)
Collapsed by default, as pi's TUI `CompactionSummaryMessageComponent` (#1026): the header, "Conversation compacted" and pi's "Compacted from N tokens" (`details.tokensBefore`, set by the reader). The title is the toggle (a button with `aria-expanded`); the description, the summary Markdown and the file lists mount only when expanded. Session search indexes only user and assistant `message` entries (`lib/session-search.ts`), so no hit lands inside a summary and the card needs no `reveal` like Process details.

## Streaming token rate
The streaming reply's `t/s` counts estimated tokens from when its first ones showed. That start lives in `lib/stream-token-rate.ts`, keyed by the reply (provider, model and request `timestamp`), not in `MessageView`: switching sessions remounts the chat, and a start taken at the remount divided every token streamed so far by a fraction of a second. A reply joined with no record (a reload) counts only the tokens that follow.

## Auto-retry banner
`auto_retry_start` shows "Retrying (n/max)…" above the composer for the backoff wait. The retried run's `agent_start` clears it, as pi's TUI replaces its retry indicator at that run's `turn_start`: pi emits a successful `auto_retry_end` only with the retry's first complete assistant message, minutes into a long reply. `auto_retry_end`, `agent_end` and settling clear it too.

## Tool execution events on the SSE stream
- Calls made through `ctx.executeTool()` (a codemode script's) emit `tool_execution_*` with `parentToolCallId` and ids `<parent>/<n>`. `toClientAgentEvent()` sends their start and end slim and drops their updates; test for nesting *before* rebuilding an update, which keeps only `toolCallId`, `toolName` and `partialResult` (a nested update would reach the browser as a top-level tool). `handleAgentEvent` keeps them out of the running-tools phase; `AgentSessionWrapper` never records them for replay, a parent's end forgets every id under `<parent>/`, and `agent_end` clears the replay set.
- `tool_execution_end` never carries `result` (up to 1 MiB of bash output): the browser renders the tool result message that follows. `entry_appended` is omitted. A codemode update's `details.calls` keeps the newest 200, `omittedCalls` counting the rest.
- `createAgentEventStream()` coalesces `tool_execution_update` per `toolCallId` (latest wins, `TOOL_UPDATE_COALESCE_MS`) and discards that id's pending update before forwarding its `tool_execution_end` (`agent_end` discards all), or the tool would read as running again. Everything else goes at once, so a pending update can arrive after unrelated events.
- A codemode card shows the script in the box any tool's input uses (plain text) and its `details.calls` as rows, never as cards: those calls never reach the model as tool calls. `handleAgentEvent` keeps a running script's progress snapshot in `activeToolResults`, as for shell output, so calls list while they run.

## Transcript system messages, usage entries and context edits (pi >= 0.86)
- A new session's first request persists a `message` entry with `role: "system"` (prompt sections, tool declarations); prompt or tool changes append more, announced with `message_start` / `message_end`. They are provider input, never conversation: `toClientAgentEvent()` drops them (they carry every tool schema), `handleAgentEvent` skips strays, `entryToUiMessage()` returns null, and `BranchNavigator` / `lib/project-tree.ts` never label or preview a branch with one. They still count toward `messageCount` and `totalMessages`, as in the SDK.
- `usage` entries (`kind: "cache_warm"`): billed prompt-cache warming outside model context; `computeSessionStats()` adds them like compaction usage so counters match the TUI's `/session`.
- `context_edit` entries omit or replace an earlier entry's model context without changing raw history; the UI ignores them. A retain-none compaction stores its own id in `firstKeptEntryId`.
- `listSessionsIncremental()` must keep `SessionManager.listAll()`'s order: newest mtime first, then reverse filename, stable for equal activity time.

## Cache and cost notices (`showCacheMissNotices`, #1265)
- pi's own setting (project `.pi/settings.json` over the global one, off by default), read on every history read and every assistant `message_end` by `readShowCacheMissNotices()`: a plain `JSON.parse` of each file cached by inode, size and mtime, never `SettingsManager.create()`, which locks each file (a `settings.json.lock` directory in the project) and busy-waits up to ~200 ms when another writer holds it; Settings › General's switch (`/api/cache-miss-notices`) writes only the global key, removing it when off. The four notices are the TUI's (`interactive-mode.js`): a significant cache miss (from 20k re-billed tokens or $0.10; "after model switch", "after Nm idle" past the 5-minute TTL), cache warming (`usage` entries, `kind: "cache_warm"`), a compaction's or branch summary's billed usage, and Anthropic dropping more thinking blocks than for the response before (`anthropic_input_transformations` diagnostics). Unlike the TUI, the thinking drop also shows in history: a reload is routine here.
- Cache misses are never persisted, so everything is derived from the entries: `collectTranscriptNotices()` (`lib/transcript-notices-server.ts`) keys them by the entry whose chat message they follow, and both history routes hang them on a copy of that message (`transcriptNotices`, `attachTranscriptNotices()`); a reload, a reconnect or an older page gives the same lines, never twice. `scanCacheMisses()` ports the SDK's unexported `core/cache-stats.js` (every entry in file order, as `getEntries()` gives it); `lib/transcript-notices.test.mjs` compares it with the installed SDK's module and `formatTokens()`, so an upgrade that changes either fails there. Cache warming follows the nearest ancestor the chat shows (a tool result is drawn inside its call), so it lands on the same message on any page; it counts only when the usage entry is on the shown leaf's branch, since that ancestor is shared with every branch forked below it.
- A total miss (`cacheRead` 0) prices the cache read from what the session's own replies paid for one with that model (`withSessionPrices()`), then an open wrapper's `modelRuntime`, else at 0 like the SDK. The live reply and every later read price it alike. Never the shared extension-loaded runtime: building or refreshing it runs extensions with no deadline, and a history read would wait on it. The switch's state is part of `snapshotRevision`'s source id, or turning it on would keep the cached messages without notices.
- Live, the wrapper adds `transcriptNotices` beside an assistant `message_end` (never on the message: pi writes that object to the file), skipping the message if pi already appended it; `useAgentSession` hangs them on the message it appends. Cache warming and summary costs arrive with the reload after `agent_end` or the compaction; an idle-mode warming with no run shows on the next read.
- `ChatWindow` draws each message's notices under it (`TranscriptNoticeLines`; amber, cache warming dim) from the stored message, not a turn view's copy, so the final answer's go under the answer and not again inside Process details. A step that shows nothing else keeps its notice lines, not counted as a message. Folded, Process details adds the cache misses inside it to its header (`summarizeCacheMisses()`); open, the header drops that part and each line shows under its step. A compaction's cost is a line in its card.

## Turn grouping and custom messages in the chat (`ChatWindow`, `lib/message-display.ts`)
- A turn runs from one anchor (`isMessageGroupAnchor()`) to the next; its last assistant answer shows, everything before it folds into Process details. Anchors: user messages, the compaction summary, and background subagent completions, which arrive as a follow-up that triggers a new run after the answer: pi-web's `pi-web:subagent-notification` and `@tintinweb/pi-subagents`' bare `subagent-notification` (#891, #1075). Without the anchor, the reply to the notification becomes the turn's answer and the real one folds away.
- A custom message without `display` (`display: false` keeps it for the model alone) stays in `messages` and `entryIds`, from the reader and from `message_end`, but renders nothing, as in pi's TUI: `isHiddenCustomMessage()` makes `renderMessage()` return null, keeps it out of the Process details count, and it never anchors a turn. An extension may send one on every `session_start`, i.e. on each idle restart (#1043).

## Running state polling + reconciliation
- The sidebar polls `/api/agent/running` every 2.5 s while the tab is visible; the session-list response is the initial fallback.
- The same poll carries `awaitingInputSessionIds`: the running sessions with an unanswered blocking `extension_ui_request` (`isBlockingExtensionUiRequest()`, `lib/extension-ui-queue.ts` — select / confirm / input / editor, or a custom overlay that has not closed), as `AgentSessionWrapper.isAwaitingInput()` reads `pendingUiRequests`. The row shows that in the spinner's slot as an amber breathing dot (the unread dot's shape and animation) and stays a running row everywhere else: same `is-running` class, no archive button, group and pinned-header counts unchanged, the archive predicate untouched. The wrapper checks `isRunning()` first, so a custom overlay that outlives its turn is not a parked run. `/api/agent/running` is the only source: a background session's own SSE stream has no listener, which is why the browser notification (`#431`'s `handleAttentionNeeded`) cannot cover this.
- The list's `firstMessage` is a row title, not the prompt: `catalogFirstMessage()` sends a skill expansion as its `/skill:` command and cuts the rest to 500 code units (persisted rows and live ones from `getRpcSessionInfos()`). Whole first messages made the list 3.2 MB (one row 325 KB), fetched again by every tab after each run. Fork naming reads the file itself and is unaffected.
- A run's end costs one list rebuild: the wrapper invalidates the list at `agent_end`, before the event reaches any browser, so nothing after it forces one. The tab showing the session reloads through `refreshKey` (`handleAgentEnd`; the reload's row reaches the selected session through `handleSessionsChange` → `mergeCatalogRow()`, which also clears a fresh session's `transient`), the others through the version poll and the background-completion reload, all plain `loadSessions()`. A `force=1` there rescanned again and bumped the version, so each tab not showing the session made every other tab reload once more (5 list requests and 3 rebuilds per run with two tabs). Only the first page load's details hydration still forces, to pick up what the pi CLI appended meanwhile.
- A name set through `AgentSession.setSessionName()` invalidates the list as well, on the wrapper's `session_info_changed`: an extension's title (pi-autoname, pi's `examples/extensions/session-name.ts`) lands after `agent_end` or with no run at all, and the sidebar kept the old name until something else bumped the version (#1237). The open chat's name (`selectedSession.name`) follows through the version poll and `handleSessionsChange`; the state route carries none.
- `invalidateSessionListCache()` bumps the generation but **keeps** the previous scan, fresh only while its generation matches. Callers needing only metadata (search hits to sidebar rows) pass `listAllSessions({ allowStale: true })` to read it while it rebuilds in the background, accepting that a seconds-old session is missing.
- `useAgentSession` treats per-session SSE as primary and opens it before each prompt. `prompt_done` completes the UI stage and notification at once, but the stream stays open for the next prompt: the selected session's while selected (`scheduleEventStreamClose()` skips it), any other's for a 30-second grace window. `agent_start` cancels the close timer; `agent_settled` finishes extension-injected runs that have no wrapper-level `prompt_done` and starts a fresh grace window. Never close on the first `agent_end`: retries, compaction and extension-queued messages continue the same logical prompt.
- While a run is active, `useAgentSession` polls `GET /api/agent/[id]` and reconciles on `visibilitychange` / `online`, for terminal events missed by background tabs or half-open connections. Busy replies also refresh context usage; each completed assistant message requests an immediate usage read between model calls. Usage reads from mount, message completion, reconciliation and `agent_end` share a monotonic request id and check the current session/run and mounted hook. A reply applies only when its id is newer than the last applied one, so a delayed read cannot overwrite newer usage, and a newer read that fails does not discard an older one still in flight. Each mount marks the reads started before it as stale.
- Prompt runs carry a monotonic run id; late SSE or reconciliation answers from an old run must be ignored, or they resurrect stale streaming bubbles.
- Every SSE (re)connection is gated on `sessionHookMountedRef`. Under React Strict Mode (`next dev`) the mount-only effect's cleanup clears it and restores it only after the warm-session effect re-runs, so that effect must re-assert it before `maintainEventsConnected()`, or a dev tab never opens its stream.

## Extension status bar and command buttons (`components/ExtensionStatusBar.tsx`, `ExtensionWidgets.tsx`)
- `ctx.ui.setStatus(key, text)` lands in the wrapper's `extensionStatuses` map, reaches the page as an `extension_ui_request` (`setStatus`), and is restored from `GET /api/agent/[id]` state after a reload. The shelf under the composer shows one cell per status in key order (like Pi's footer), separated by vertical rules. The widget triggers share one `extension-status-row` with the status line so the row scrolls sideways as a whole; the expanded widget panel stays above it, outside the scroll.
- A key `command:/name args` makes its cell a button that sends that slash command through `handleSend` (disabled while the session is busy). The command lives in the key because `setStatus` has no room for it, and Pi's own footer prints only the text, so the same status is plain text there. Only `/…` commands qualify: anything else would reach the model, and `!` would run a shell command.
- A status with nothing visible (empty after stripping ANSI) gets no cell. Touch screens get 44px cells (widget triggers included) only when the bar has a command button.
- Statuses exist only while the session's wrapper is alive, so a fresh chat or a session nobody has prompted yet shows no cells (and no buttons) until its first message.

## Exported session HTML
- `/api/sessions/[id]/export` delegates to pi's export helper, then makes the generated HTML's recursive tree helpers iterative, so very deep linear sessions do not overflow the browser call stack.

## Message list props stay stable (`components/ChatWindow.tsx`)
- ChatWindow re-renders on every chat update (streamed chunks aside, see below): tool results, notices, statuses, and each render an extension's custom panel sends (one or two per key typed into it). `MessageView` and `MarkdownBody` are `memo`'d, so each prop the list hands them keeps its identity while the transcript is unchanged: `toolResultsMap` is memoized, and a grouped turn's answer and process copies and its written-files list come from `getFinalAnswerViews()` / `keepWrittenFiles()` (`lib/turn-views.ts`), cached per stored message. Copies built inline re-ran every visible answer's markdown per keystroke (#1005).

## A run's messages keep their keys (`lib/message-keys.ts`)
- A message's React key is its entry id, but one added during a run (the sent prompt, each `message_end`) has none until the file is read again: at the run's end, at the `agent_end` before an auto-retry, at `compaction_end`. pi persists a message only after emitting `message_end` and never announces its id. Keyed by its index until then, it remounted on that first read and lost its DOM state: the prompt bubble's inner scroll, open thinking, a tool output's scroll (#1184).
- Such a message is keyed by its place after the last loaded entry (`live:<anchor>:<offset>`), which appends and older pages leave alone. `loadSession`'s replacing read hands those keys to the entry ids at the same places after the anchor (`carryMessageKeys()`; the hook keeps the aliases while their ids are loaded), each checked against the message it replaces: `userMessageKey()` for the prompt (sent with the browser's timestamp), `customType` for a custom message, `timestamp` for the rest. From the first mismatch on, or when the window no longer holds the anchor (a run past the first page), messages keep their id keys and remount as before. Fork, search and `data-entry-id` still read the real `entryIds`.
- A kept message keeps its blocks too: `AssistantMessageView` keys a block by its index (`${entryId ?? "stream"}-<index>` re-keyed every block on that read), so open thinking, a tool card and its output's scroll survive it. `ThinkingBlock` drops what it loaded (`content`, `loading`, `error`) when its session, entry or block index changes, so a reused block never shows another entry's thinking; an open block the read turns `deferred` shows "Loading thinking..." until its full text arrives. The run's end still remounts the process messages as they move into Process details (another parent), and an answer that followed thinking in its message (its blocks move up as the thinking leaves); that is the grouping, not the read.

## Streamed chunks re-render only the reply

- `lib/streaming-message.ts` 的 `StreamingStore` 保存流式消息，`useAgentSession` 返回稳定 store；`useFrameBatchedStreamDispatch` 继续按浏览器帧合并增量。`ChatWindow` 只通过 `useStreamingSelector` 订阅是否流式、有无内容和可见块数，`components/StreamingReply.tsx` 单独订阅完整消息。普通正文增量不重渲窗口或输入框；块增删时仍更新 fork 的运行中过程折叠窗口。
- store 同步通知订阅者，使 `message_end` 的 flush、追加完成消息、清空回复仍同批提交。会话身份变化重置帧队列，原有 run id 校验继续拒绝过期事件。`ChatInput` 和 `ChatMinimap` 保持 memo；minimap 通过稳定 getter 在测量时读取流式消息，滚动跟随继续使用 fork 的 `useChatScrollFollow`。
- `components/ChatWindow.streaming.test.mjs` 执行真实 hook、窗口与输入框，用 React Profiler 验证 30 个增量至少产生 30 次回复提交（测试冻结独立的滚动/时钟计时器，只统计 SSE 引起的更新），而窗口和输入框均不新增渲染，同时核对 DOM 正文、顺序、flush 和会话切换。文本块稳定 key 下必须直接渲染当前 `block.text`，state 只保存按需加载的完整正文。

## Streaming markdown renders block by block (`components/MarkdownBody.tsx`, `lib/streaming-markdown-blocks.ts`)
- 保留 fork 的 `splitStreamingMarkdown()`：仅在安全的顶层空行切分，避开未闭合围栏、HTML 块和注释、数学块、列表/引用续行以及引用链接和脚注定义。冻结块使用 memo，只有尾部重新解析；未闭合代码围栏走纯文本快路径。行内 HTML 不会使整篇分块失效。
- 流式结束后仍整篇渲染，最终 Markdown 输出保持完整语义。渲染回调通过 ref 读取，避免回调身份变化破坏冻结块 memo。修改切分规则须运行 `lib/streaming-markdown-blocks.test.mjs`。
- `onNavigateLink` (Settings › Skills) hands a document reader its local links: an anchor with `role="link"` and no `href`, so no click, middle-click or "Open in new tab" loads the path on the app's own URL; an empty (sanitized) `href` and HTML anchor destinations render as in chat. It also switches to `markdownDocumentRehypePlugins`, which give headings github-slugger slugs as `data-heading-anchor` (never an id, so two readers cannot collide), set after sanitizing and before KaTeX writes each formula's text twice. Chat rendering is unchanged.

## Long thinking renders in pieces (`ThinkingBlock` in `components/MessageView.tsx`, `lib/message-display.ts`)
- Thinking is plain `pre-wrap` text, never markdown. A model looping in its thinking writes megabytes (#1196), and as one text node the expanded block was laid out whole again on every streamed chunk (`StreamingReply` reads the prompt anchor's layout after each commit): in headless Chrome at 4x CPU throttling, 440 ms per chunk for 500k Chinese characters, so the page never caught up. `splitThinkingPieces()` cuts at the first line break past each 8,000 characters, and `ThinkingText` renders one div per piece. A cut depends only on the text before it, so while thinking streams only the last piece changes: 6 ms per chunk there. The line break at a cut is left out of both pieces and the block boundary stands in for it, so the lines, `innerText` and a selection's text are the single node's (headless Chrome). A line break that ends an empty line is never a cut: the piece would end in a line break, which a block draws no line for, and that empty line would be lost. Thinking that fits one piece is the one text node it was.
- A piece with no line break by 16,000 characters is cut there (a code unit earlier rather than inside a surrogate pair), so a loop that never breaks a line gets pieces too: at 1x, 500k Chinese characters went from 1,082 to 4 ms per chunk (and from 1,061 to 134 ms to expand), 2M English ones from 120 to 0.6 ms. That cut leaves nothing out, so it shows: a line end every ~16k characters of an unbroken line, and one more `\n` in a copy across it.
- The pieces are plain divs, not `memo`'d: React already leaves a div whose text is unchanged alone. A memo bailout keeps the old props, and each old piece is a V8 slice pinning the whole thinking string of the chunk it last changed in: streaming 2M Chinese characters retained 995 MB until the reply ended, 9 MB without memo (React 19 in headless Chrome).
- Expanding a finished block still lays out all of it once, as before (about 500 ms for that text at 4x). `content-visibility: auto` on the pieces would skip the ones off screen (70 ms to the first frame), but its placeholder heights, about half the real ones in the bench, change the scroll height as pieces come into view; it is not used.

## Exported session HTML
- `/api/sessions/[id]/export` delegates to pi's export helper, then makes the generated HTML's recursive tree helpers iterative, so very deep linear sessions do not overflow the browser call stack.

## Deleting the selected session outlives the delete click (`components/AppShell.tsx`)
- `SessionItem.performDelete` captures `onDeleted` at the delete click, and `handleSessionDeleted` is a `useCallback` whose `selectedSession` closure is from that same render. The DELETE request can complete **after** the user has switched sessions, so the captured selection still names the session being deleted.
- The empty-composer fallback therefore guards on the latest selection read from a render-synced ref (`selectedSessionRef.current`), not the captured state, and takes the fallback cwd from that ref too: a user who navigated away stays on their new chat, and a user who lands on the deleting session in flight still gets a fresh composer in its cwd.
- `setRefreshKey()` and `invalidateWorkspaceRestore()` run unconditionally, so the sidebar list and any pending workspace restore never resurrect the deleted session.

## A link to a session that is gone (`components/AppShell.tsx`, `lib/initial-navigation.ts`)
- When the sidebar's list lacks the `?session=` id (`linkedSessionId()`), it toasts `sidebar.sessionNotFound` and `handleInitialRestoreDone` sets `skipWorkspaceRestoreRef`: the next `handleCwdChange` (the sidebar adopting its most recent project) shows a fresh composer instead of `restoreWorkspaceContext()`'s last open session, which the URL would then name (#1168). Later project switches restore as before; a gone session only this tab remembered (`sessionFromTab`, from `withTabOpen()`) still falls back as a fresh tab does.

## External session file discovery (`checkSessionMembership()`, `lib/session-list-scanner.ts`)
- Sessions the pi CLI (or any other process) creates or deletes bump no `sessionListVersion`, and the 30 s list cache's age is only looked at when a list is requested, so the sidebar's running poll never reloaded for them. `getSessionListVersion()`, which that poll calls every 2.5 s, now starts a filename check: it lists `sessions/<cwd>/*.jsonl` (`enumerateSessionFiles()`, directory reads only, no transcript opened) and invalidates the list when the set differs from what the last scan listed (`listSessionsIncremental()` records it). The poll that follows sees the new version and reloads.
- Appends never change a filename, so a running session costs nothing here: no rescan, no reload. Content rewritten under the same name is not a membership change either; in-process writers invalidate on their own as before.
- One check at a time, at most one per second (`SESSION_MEMBERSHIP_CHECK_MS`) whatever the number of tabs, none before the first scan. A change is recorded as it is reported, so it bumps once, not on every poll until the rescan. A scan that records its listing while a check reads replaces the baseline and the check's result is dropped: comparing an older read against a newer scan would bump for nothing, and the next check compares against the scan anyway.
- No `fs.watch`: a recursive watch on Linux is Node's JS layer (one inotify watch per file and folder, a synchronous walk of the whole tree when it starts, and a silently partial watch at the inotify limit), and on macOS it reports appends as `rename`. A missing sessions directory counts as empty; a changed `PI_CODING_AGENT_DIR` is just another listing. The cost is a readdir per project folder per second while some tab polls (about 10 ms for 18,000 files).

## History caches and deferred highlighting (`lib/session-reader.ts`, `lib/session-view-cache.ts`, `lib/highlight-queue.ts`)
- `GET /api/sessions/[id]/entries/[entryId]/tool-result-image?blockIndex=` answers `private, max-age=31536000, immutable`: a session's entry id and block index name the same bytes for good (pi only appends, a migration's rewrite keeps every entry, a `context_edit` leaves raw history alone). With `no-cache` every view re-sent multi-MB images and decoded their base64 again. Error replies carry no cache header.
- A list rebuild reads a fork's or subagent's run (`readSubagentRun()` over the file's bounded head and tail) once per scanned row: `listSessionsIncremental()` hands back the index's same row object while the file's size and mtime hold, so a `WeakMap` keyed by the row caches the run. A rebuild on 355 sessions (137 subagents) went from 36 ms to 7 ms, synchronous reads that blocked the event loop. A row the scanner makes anew (a changed file, a restart) is read again; a failed read is not cached.
- `listSessionsIncremental()` parses a file that only grew since its last scan from just past the last newline that scan read (#1259): the index keeps that offset with the row's running totals, the file's inode and a hash of the header line plus the 512 bytes before the offset, so a file replaced by a rename (sed -i, an editor, git checkout), a rewrite in place that changes the header (pi's migrations, delete's reparenting), a same-size or shorter file, or an unterminated last line that counted gets a full read; a same-length edit that keeps the inode, the header and those 512 bytes is missed, and stays missed through later appends. Lines end at `\n`, `\r\n` or a lone `\r`, as the scan's readline did on Node 22; a raw U+2028/U+2029 (JSON.stringify leaves both raw), which Node 24's readline and so `SessionManager.listAll()` split on, stays in its line, as pi's loader keeps it. An appended line on a 150 MiB session went from 260 ms to under 1 ms; `pi-web-session-index.json` is written at most once per 5 s (a trailing throttle, into the agent dir of the scan that queued it), not after every listing.
- `lib/session-view-cache.ts` measures a snapshot (its `JSON.stringify` length) once, when it is stored, and evicts by the stored sizes: snapshots are never mutated in place. Re-serializing every cached session on each store took 7.7 ms with eight 0.8 MB snapshots (1.3 ms now), at every run's end, compaction and session switch. The unmount check for a wider cached window is `snapshotCoversLoadedEntries()` (a `Set`), not nested `includes`.
- Code fences (`CodeBlock`, `components/MermaidBlock.tsx`): Prism tokenizes in the render, about 5-10 ms per 1,000 characters of TypeScript on a desktop. Within one task the first 2,000 characters of fences are highlighted at once (`takeHighlightBudget()`); the others render through the same `SyntaxHighlighter` as `text` (same lines, numbers and box, no tokens) and take their language one per idle slice, newest first (`waitForHighlight()`; Safari has no `requestIdleCallback` and waits 50 ms). Opening a session with 86 fences at 4x CPU throttling, the commit that shows the messages went from 1.1 s to 0.66 s; the end of a streamed reply gets the same budget. `codeTagProps` sets no class, so tell a highlighted fence by its `span.token` elements other than `.linenumber`, not by a `language-*` class.
- Prism languages load on demand (`lib/prism-languages.ts`, `hooks/usePrismLanguages.ts`). `CodeBlock` and `FileViewer` render with `react-syntax-highlighter/dist/esm/prism-light` (refractor's core), never the package index: its `Prism` imports `refractor/all`, which registers about 300 languages when evaluated, ~650 ms of the first `AppShell` render at 4x CPU throttling on every page load, code on screen or not. The first highlighter to mount imports `refractor/all` as a chunk of its own; it registers into the same core instance, so every language and alias works as before. Until then fences render as `text` and files as `plaintext` (same lines, numbers and box). A page with no code never loads it. Client code imports only types from `react-syntax-highlighter` itself.
