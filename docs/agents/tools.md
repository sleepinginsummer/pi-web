# Tool selection and built-in extensions

## New session tool preset
Tool names are passed at session creation (`POST /api/agent/new` → `toolNames[]`) and persisted in versioned `pi-web:tool-selection` custom entries (ADR 0002). No entry, or a later `cleared: true` one, means no pin: the session follows pi's `defaultTools`, as the `configured` preset ("From Settings", the Built-in tools row of Settings › General) does by sending no `toolNames`. An empty array is Chat only, resolved before services are created: no extensions/skills/prompts/themes, and the ordered contents of Pi's discovered context files replace Pi's base prompt. Crossing the Chat-only boundary or clearing a pin rebuilds the wrapper; changing between nonempty presets updates it in place.

**Chat only has no extension providers** (#804): the model selector's listing loads extensions, the session does not. A model only an extension provides (one `findDeferredModel()` remembers but the Chat-only runtime lacks) is named as such: a start refuses it when the browser chose it, `set_model` refuses it instead of "Model not found", and a prompt in a session that could start on no model at all names the one it wanted rather than pi's "No API key found". With no pick, another model in scope stands in for an extension's default, as for any default out of scope.

**Exact system prompts go through `before_agent_start`.** Chat-only sessions register `lib/exact-system-prompt.ts` as an inline extension factory, and subagents (any profile in replace mode, or one naming `skills:`) the equivalent handler in `lib/subagent-skills.ts`, which appends the named skills or, in replace mode, pi's skill catalog; the handler returns `{ systemPrompt }`, which the SDK sends as the provider's leading system prompt for the run while the transcript keeps Pi's structured sections. Assigning `agent.state.systemPrompt` (a getter replayed from transcript system messages) throws, and patching `prepareNextTurnWithContext` never reaches the model. `get_state.systemPrompt` reports the exact prompt for those wrappers. Subagents persist their tools and the profile's skill / extension switches in `resourceSnapshot`, and extensions never expose the reserved `Agent`, `get_subagent_result` or `steer_subagent` to them (ADR 0002).

The last preset the user explicitly selected is kept in browser `localStorage` and initializes fresh-session composers only; a browser without a stored pick starts on `configured` (`getPreferredToolPreset()`'s fallback), so the switches in Settings › General still decide what a new session gets (#700). Under `configured` the menu's checklist is display-only: it shows the built-ins that selection resolves to (`/api/tools/settings` `builtinTools` for a fresh composer, the session's live active tools afterwards), disables every box, and says to change them in Settings — that list is the global `defaultTools`, so a per-session tick would fork it silently. From any other preset the boxes are editable, and ticking one produces a custom list for that session (remembered for later fresh composers). The chip shows what the session **recorded**, not what its live tools match: `get_tool_selection` answers the active branch's persisted pin (`null` = follow settings, `cleared` counts as none, `getBranch()` so a recording made later on does not leak onto an older branch the runtime restored), and a pin that matches a preset shows that preset, a free-form pin shows "Custom". Deriving it from live tools instead made an extension that removes a built-in (pi-hashline-edit-pro replaces `edit` with `replace`/`insert`) turn `configured` and `full` into "Custom" by itself. The gap is reported per row instead: a built-in that `defaultTools` enables but this session runs without gets a muted "Replaced by an extension" note, computed by `missingBuiltinTools()` from that expectation against the live `get_tools` set, so a preset that deliberately leaves a tool out is never labelled. Chip and preset rows take their names from `toolPresetLabelKey()` — one i18n vocabulary, so no English `full`/`configured` next to a translated "Custom" — and a row whose description would repeat its name drops the description. Existing sessions never trust the preference: a pinned one shows its selection (`toolNames` from `GET /api/sessions/[id]`, then its live `get_tools`), an unpinned one `configured`. `handleToolPresetChange()` moves the chip and the checklist only after `set_tools` is confirmed (a fresh session applies them at once, since that pick is what the session will be created with): the change can be refused, for example while messages wait only for Recall, and a chip that already shows the new preset would claim tools the model does not have. While that request is in flight the chip and the boxes are disabled (`toolSelectionPending`) at all four entry points — the desktop `InputControls`, the phone's `MobileComposerMenu`, the `ComposerTopUtilities` row and the `ChatInput` call sites that feed them — and a second call is ignored before any browser preference is written: the candidates are still the confirmed list, so a second click would send a request computed from the same stale list and the later answer would turn the earlier tool back on, while a preference written from that list would hand a new session a selection the user never confirmed. For the same reason the browser preference (`setPreferredToolPreset` / `setPreferredCustomTools`) is written only after `set_tools` is accepted on an existing session (the fresh-composer path writes it immediately, since that pick is what creates the session): a refusal — running, compacting, a `!` command, or messages waiting only for Recall — left the old default in place, and the next new session came up with a selection that had never applied. A fresh composer's pick is also recorded in the draft state (`SET_TOOLS`, per cwd, shared through `lib/pending-new-session-mirror.ts`), and creation reads that record rather than the browser preference: the preference is one value for the whole browser, so another tab changing it — or a refused `localStorage` write — would otherwise let the request use a list the composer never showed. The preference only initializes a draft whose tools were never touched.

**A busy session makes the preset menu read-only.** `setRpcSessionTools()` refuses a running session ("Cannot change tools while the session is running"), and its `isRunning()` also covers a manual compaction and a `!` command, so the chip stays clickable (`locked`) whenever the composer is busy: the menu opens, one muted line at the top says the selection cannot change yet (`chat.toolsLockedWhileRunning`, or `chat.toolsLockedWhileCompacting` while compacting), and every preset row is inert. `ChatInput`'s `isStreaming` is `sessionBusy` (agent run or `!` command) and each of the three control entry points adds `isCompacting`, so a manual compaction can no longer write a tool choice the server refuses. The tools themselves come from `get_tools` (`activeToolNames`), not from the recorded preset: the read-only section lists the names this session actually has active, extension and MCP tools included, and the preset rows above it stay as the recorded choice. Reading the checklist off the preset instead was wrong at a run: a `configured` session that restored an older pin while global `defaultTools` later enabled `write` showed `write` ticked although the session never had it, and the fixed four built-ins could not show an extension's own tools at all. The list is re-read every time the menu opens in that mode (`refreshTools` → `loadTools`, discarded when the session changed meanwhile): a cold session's first snapshot can arrive before its runtime exists, so mounting skipped the read, and a Shadow Mind switch changes the server's active tools mid-run. Names stay exactly as `get_tools` reports them — a PowerShell session lists `powershell`, and only `normalizeBuiltinToolName()` folds it back to `bash` for preset inference and the "replaced by an extension" note. An empty list is shown as "no tools enabled in this session" (`chat.toolsNoneInUse`) instead of the unavailable text, which belongs to a missing `activeToolNames` only. The list scrolls inside the menu (the session can carry dozens of MCP tools), and on the phone the flyout is positioned against the controls panel (`position: static` on the button's wrapper, so `.mobile-controls-menu` is the containing block) and capped at `calc(100vw - 24px)`: the tool row is the panel's first item during a run, and a 120px-minimum menu right-aligned to that button hung off the left edge of a 320px screen. Its placement and height are measured from that panel's real `getBoundingClientRect()` while open (`toolDropdownFit`, one effect keyed on `isMobile`/`toolDropdownOpen` that also listens to `resize` and `visualViewport`): it opens upwards while 140px or at least as much room as below is free, otherwise downwards, and its `maxHeight` is exactly the remaining room on that side — the earlier `Math.max(140, …)` floor still pushed the top out of a viewport that had less. Measured on a 320×800 viewport: flyout 57–287px wide, top 4px, scrolling inside, instead of a left edge at −140px. The chip's tooltip and `aria-label` switch to `chat.viewToolPreset`, so nobody reads the greyed rows as a broken button. A switch still in flight (`toolSelectionPending`) is different: the candidates are stale then, so `disabled` keeps the whole button inert — it ignores clicks and closes an already open menu. The control stays positioned after the reasoning control in both layouts, so the phone's controls panel shows the two rows during a run (the idle-only Fast row drops out).

**Tool exposure.** pi activates `direct` and `model-only` tools on registration unless their definition sets `defaultActive: false` (`codemode` and `tool_search` do), leaves `codemode` and `deferred` tools undeclared until something activates them, and ignores `hidden` (withdrawn) tools in `setActiveToolsByName()`; `get_tools` leaves hidden tools out.
- Pi Web's environment-sanitizing `bash` (`lib/project-command-env.ts`, ADR 0001), an extension tool standing in for pi's built-in, sets `defaultActive: false` too, so like the built-in it is on only when `defaultTools` (pi's default list included), a preset or `set_tools` names it; registered active, it came back in every session whatever `defaultTools` left out (#1235). A user extension's `bash` still replaces it (`preferUserBashExtension()`) and activates as in the CLI. `powershell` (the Windows PowerShell switch) gets the same stand-in from its own extension (`createProjectCommandPowerShellExtension()`, `preferUserPowerShellExtension()`), so a user's `bash` or `powershell` replaces only the tool it names; pi's built-in would run commands with the server's whole environment.
- `get_tools` reports an active tool's description from `agent.state.tools`, what the model is sent. Under `codemode.mode: "only"`, while `codemode` is active, the active `direct` tools stay active and callable (`get_tools` reports them so, with `declarationHidden: true` from the AgentSession's private `_hiddenDeclarations`), but codemode's `hiddenDeclarations` leave their declarations out of every request, so the model reaches them only from scripts. The toolbar's Tools panel lists only what requests declare; presets still read `active`. A preset still bounds them: a `direct` tool is callable only while active. `prepareLoadout` hooks rewrite it there on every loadout change (tool registration included): codemode's definition holds only the intro, while the declared one lists the tools scripts can call, MCP namespaces and types, and appends the codemode declaration to the callable `direct` tools.
- A preset replaces only the coding tools. `resolveActiveToolNames()` carries every other tool that is active, registered and not hidden, so what an extension, `tool_search` or a `defaultTools` entry such as `+codemode` activated survives startup, `set_tools` and `reload`, a tool an extension switched off stays off, and a preset never turns `codemode` on. It adds nothing else: pi activates extension tools itself, so re-adding them would override an extension (or a branch's recorded loadout) that keeps a `direct` tool off. `reload` carries the set pi rebuilt after extensions restarted, not the previous one.
- `navigateTree()` restores the target branch's loadout from its transcript (bringing back `write` under a Read-only pin, dropping `codemode`), so a normal session then reapplies its pin (the restored set when unpinned) and carries over from the branch it left the session's own tools: `codemode`, `tool_search` and pi-web's subagent tools. Other extension tools follow the target branch's loadout, as in the pi CLI; since pi 1.4 (#11062) one that branch never added or removed, such as one registered after that branch point, is active unless it is registered with `defaultActive: false`. When pi restores the same set that was active (editing a history message, or going back to a point after the last tool change), the session keeps the order pi restored: pi replays the branch's recorded loadout, so that order is that point's prompt (#1405). Reapplying keeps the carried positions of the survivors and appends newly selected coding tools at the end, so the prompt's `<tools>` section stays byte-identical with the `pi` CLI's for the same set; regrouping the coding tools ahead instead rewrote it and dropped the prompt cache on every harness switch. Chat-only and subagent wrappers keep what pi restored.
- A reopened normal session starts on the loadout its transcript last recorded (pi 1.3, as `pi --resume` without `--tools`: pi-web passes no `tools`), not on today's `defaultTools`, so `+codemode` or another `defaultTools` edit made since reaches only new sessions and transcripts that record no loadout. An unpinned session keeps the recorded tools; a pinned one gets its pin over the coding tools and carries the rest from that loadout. Chat only (`tools: []`) and subagents (`subagentToolOptions()`: an allowlist, or `noTools: "builtin"`) select their tools explicitly, so pi restores nothing for them.

**Built-in extensions** (`lib/builtin-extensions.ts`, ADR 0006). The CLI's built-in `codemode`, `tool-search` and `mcp` are rebuilt from the factories the SDK root exports, under the CLI's names with `replaceable: true, builtin: true`, so `-builtin:<name>`, project overrides, replacement by a third-party extension and `noExtensions` behave as in the CLI. Normal sessions load all three. Subagents load `codemode` through their profile's `codemode` policy, and `tool-search` and `mcp` with an MCP host of their own only under `mcp: on` (see [subagents.md](subagents.md)); they never share the normal session's.
- The MCP extension's `loadConfig` returns no servers (only `autoEnableCodemode`), so it connects nothing, and with `startupWaitMs: 0`, so its first-prompt wait for `direct` servers (which ignores Stop, and since pi 1.0 also sees servers registered right before the prompt) holds nothing; pi-web registers servers itself (**MCP host** in [mcp-runtime.md](mcp-runtime.md)). Servers connect through `createPiWebMcpTransportFactory()`; `openUrl` opens no browser on the server host.
- MCP is off (the `mcp` entry registers nothing) when `PI_WEB_DISABLE_MCP` is anything but empty, `0` or `false`, or `lib/pi-sdk-internals.ts` cannot load; never fall back to the SDK's own transport.
- `codemode` is offered only after a self-test ran a script through the SDK's sandbox (`checkCodemodeSandbox()`, on the first normal session). A pass is kept for the process; a failure only for a minute, then the next session or subagent starting runs it again (Settings keeps showing the failure meanwhile). Its 10 s deadline counts only time the event loop was free, a late tick as at most two (30 s of wall time at most), because a synchronous stall of the busy first session start fired a plain timer before the poll phase delivered the worker's answer, and the cached failure then turned Code mode off until a restart (#1615). A built-in that cannot run keeps its `builtin:<name>` entry with an empty factory, so a setting naming it means the same.
- pi lets at most two codemode workers live per process, across all sessions (`DEFAULT_MAX_CODEMODE_WORKERS` in the SDK's `dist/extensions/codemode/execute.js`); `PI_CODEMODE_MAX_WORKERS` changes it, read on every script. Since pi 1.4 a script at capacity waits for a free worker in arrival order, up to 60 s or its `timeout_ms`, then fails without running (pi 1.3 failed it at once with "Codemode worker limit reached"). A script holds its worker while it waits on its tool calls. The CLI runs one session per process; pi-web runs every session and subagent in one, so two parent scripts waiting on subagents took both workers and every script those subagents ran timed out. `applyCodemodeWorkerDefault()` (`lib/codemode-workers.ts`, from `instrumentation-node.ts` at server start) therefore sets the variable to 8 when it is unset or empty; any other value the user set is kept, even one pi rejects (it then uses 2). Each worker's QuickJS heap is capped at 256 MB. Eight parent scripts waiting on subagents at once still fill it; only pi releasing a worker while its script waits would end that. `lib/codemode-workers.test.mjs` fails if the SDK stops reading the variable per script.

**Read-only MCP policy** (`lib/mcp-read-only-policy.ts`, normal sessions; subagents with `mcp: on` have their own, `createSubagentMcpPolicyExtension()`, which reads the profile's tools instead of a pin). While the pinned selection is read-only (it names tools, none of `bash`, `powershell`, `edit`, `write`; no pin is not read-only), its `tool_call` handler blocks every MCP tool (the MCP extension's, or any named `mcp__`) whose definition lacks `annotations.readOnlyHint: true`, codemode scripts' calls included. It reads the pin from the session entries, which `set_tools` writes before applying it and cannot change mid-run. The hint is the server's word: this guards against model mistakes, not a malicious server.

**`defaultTools` switches.** Code mode's Always on is `+codemode` in the global `defaultTools`; Automatic writes nothing (ADR 0006). `/api/tools/settings` is the only writer of that key, for this, the PowerShell switch and Settings › General's built-in tool switches, and of the global `codemode.mode` and `codemode.inlineBudget` (Settings › MCP's Built-in tools switch and tool list budget), through `lib/global-settings-file.ts` (the lock pi's `SettingsManager` takes on that file). `lib/codemode-settings.ts` edits only entries naming `codemode` and appends `+codemode`, valid on plain and modifier-only lists; a modifier-only list left empty is removed, since `defaultTools: []` means no tools at all. `defaultTools` may hold `+name` / `-name` modifiers: read it resolved through `SettingsManager.getDefaultTools()`; `lib/powershell-settings.ts` resolves the raw global list by the same rule before editing, since appending a plain name to a modifier-only list drops pi's default tools.
- **Built-in tools** (Settings › General, #1611): the switches choose the built-ins (`SETTINGS_BUILTIN_TOOLS`) the global `defaultTools` resolves to, which is what the `configured` preset gives new sessions; a per-session choice stays the presets' (or the API's `toolNames`). `withBuiltinTools()` (`lib/powershell-settings.ts`) drops only entries naming a built-in and keeps every other entry and modifier. Without another plain name it writes the built-ins as `-name` / `+name` against pi's defaults, so pi's defaults alone remove the key and all off is `-read -bash -edit -write`; beside a plain name (an extension tool) it writes them plain, or they would drop out. On Windows `bash` is the active shell: `powershell` while the PowerShell switch is on. Turning the shell off there also turns that switch off, since `defaultTools` cannot hold a preference for a tool it leaves out.
